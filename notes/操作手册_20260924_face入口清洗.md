## 一、为什么改（事实依据）

### 1.1 脏值来自源文件，不是导入过程造成的

源文件 `data/user_face.csv` 里直接就能看到空格：

| 值 | 性质 |
|---|---|
| `上班族␣␣` | 尾随空格（真脏值）|
| `游戏宅␣␣` | 尾随空格（真脏值）|
| `家庭主妇/主夫␣␣` | 尾随空格 + 与下条同义异写 |
| `家庭主妇 / 主夫` | 斜杠两侧空格 |
| `农民 / 种植户` | 斜杠两侧空格（**合法写法**）|

`db_loader.py` 原先只按 `user_id` 去重、不做任何清洗 → 脏值原样进入 `dim_user_profile`。

**实测**：`dim_user_profile.face` 里共有 **64 个去重值含空格**（完整清单见 `docs/dim_user_profile内face列含空格.csv`，该查询同时覆盖半角空格与全角空格 U+3000）。

### 1.2 为什么必须治本，而不是继续在出口补

清洗前有 **4 个下游出口**各自写各的：

| 出口 | 清洗前状态 | 显示结果 |
|---|---|---|
| `src/export_for_validation.py` | 有 REPLACE（两个参数都写成半角，全角漏网）| `农民/种植户` |
| `src/ads_visualizer.py`（图13）| 无清洗 | `农民 / 种植户` |
| `sql/04_build_ads.sql` | 无清洗 | `农民 / 种植户` |
| PowerBI 直连 DIM | 无清洗 | `农民 / 种植户` |

同一个职业在导出 CSV 和图表里是**两个不同字符串**，违反"口径单一事实来源"。
入口清洗一次 → 4 个下游自动一致，出口的补丁可以撤掉。

## 二、清洗规则（唯一正确定义）

```python
import re

def norm_face(value):
    """职业标签规范化：去首尾空白（含全角空格）+ 斜杠分隔符统一为无空格"""
    if pd.isna(value):
        return value
    return re.sub(r"\s*/\s*", "/", str(value).strip())
```

- `str.strip()`：处理首尾半角空格、全角空格(U+3000)、制表符、NBSP
- `\s*/\s*`：处理斜杠两侧空格（Python3 的 `\s` 包含全角空格）

### 2.1 实测验证（已跑通）

| 输入 | 输出 | 说明 |
|---|---|---|
| `'大学生  '` | `'大学生'` | 去尾随 |
| `'农民 / 种植户'` | `'农民/种植户'` | 分隔符规范化 |
| `'家庭主妇 / 主夫'` | `'家庭主妇/主夫'` | 与下条合并 |
| `'家庭主妇/主夫  '` | `'家庭主妇/主夫'` | 与上条合并 → **全库唯一坍缩对** |
| `'管理层（总监/经理）  '` | `'管理层（总监/经理）'` | 括号内斜杠本无空格，不变 |
| `'二胎 / 多孩家长'` | `'二胎/多孩家长'` | 分隔符规范化 |

### 2.2 展示口径变更声明

约 17 个职业名会从 `X / Y` 变为 `X/Y`（如 `会计 / 财务` → `会计/财务`）。
这是本次决策的既定代价，必须同步到口径字典与 PowerBI（见第九节）。

### 2.3 SQL 等价写法（只在"你选择手写 SQL"时才需要）

```sql
UPDATE dim_user_profile
SET face = REGEXP_REPLACE(TRIM(face), ' */ *', '/');
```

**本次不采用**。理由：同一条规则若同时存在 Python 和 SQL 两份实现，将来改一处忘一处就会漂移。

## 三、已落地的代码改动（`src/db_loader.py`，共 4 处）

> 这一节是**变更记录**，不是"待办清单"——代码均已写入并验证。

### 3.1 `norm_face` 修正

```python
# 改前（两处错）：re.sub 只给两个参数 → TypeError；第二个参数位置放的是整个原值
return re.sub(r"\s*/\s*", str(value.strip()))
# 改后：第三个参数才是"被处理的字符串"，第二个是"替换成什么"
return re.sub(r"\s*/\s*", "/", str(value).strip())
```

`re.sub(pattern, repl, string)`：在 `string` 里把 `pattern` 换成 `repl`。
**记住这个三参数签名**，以后写正则替换不会再错。

### 3.2 `DATA_SOURCES` 里给 `dim_user_profile` 挂上清洗器

```python
"cleaners": {"face": norm_face},
```

（注意：键名是 `"cleaners"` 而不是 `"cleaners:"`。带冒号的键名会让 `source.get("cleaners")` 取到 `None`，**清洗被静默跳过且不报任何错**——这个坑已经踩过。）

### 3.3 `load_small_table` → 全量覆盖

```python
    with engine.begin() as conn:                    # 一个事务包住"清空 + 写入"
        n_old = conn.execute(text(f"SELECT COUNT(*) FROM {source['table']}")).scalar()
        conn.execute(text(f"DELETE FROM {source['table']}"))    # 先清空
        df.to_sql(source["table"], conn, if_exists="append",
                  index=False, method="multi")
```

两个知识点：
- **为什么用 `DELETE` 不用 `TRUNCATE`**：`TRUNCATE` 是 DDL，会隐式提交事务，无法和插入放进同一事务 → 插入失败就会留下一张空表。`DELETE` 是 DML，可以一起回滚。
- **为什么 `to_sql` 第二个参数从 `engine` 换成 `conn`**：传 `engine` 会另开连接、另起事务，"清空"和"写入"就变成两件事了；传 `conn` 才在同一事务内。

### 3.4 `load_big_table` → 也先清空，但**故意不**用单事务

```python
    with engine.begin() as conn:      # 只清空，独立事务
        n_old = conn.execute(text(f"SELECT COUNT(*) FROM {source['table']}")).scalar()
        conn.execute(text(f"DELETE FROM {source['table']}"))
    print(f"  全量覆盖：清空原有 {n_old} 行")
    # 之后继续分块 append（原逻辑不变）
```

为什么和 DIM 不一样：**76 万行塞进一个事务会产生超大回滚段**（InnoDB 要把整批旧值留到提交才能释放），可能撑爆 undo。拆开后万一中断，因为"清空 + 重写"本身幂等，**重跑一次即可恢复**，不必为它付大事务的代价。

## 四、加载模式设计（本次讨论的结论）

### 4.1 旧代码真正的矛盾

不是"append 还是覆盖"，而是：**它嘴上说是全量导入，手上用 append，却没有去重依据**——两头都不占。看两张表的实际差别：

| 表 | 主键 | 裸 append 的后果 |
|---|---|---|
| `dim_user_profile` | `user_id` 是主键 | **主键冲突报错**，加不进去 |
| `ods_user_behavior` | 没有主键 | **静默翻倍** 76万→152万，一句报错都没有 |

### 4.2 正确的模型是三种模式

| 模式 | 做法 | 适用 | 幂等 |
|---|---|---|---|
| 全量覆盖 | `DELETE` + `INSERT` | 快照源文件、维表 | 是 |
| 幂等追加（UPSERT）| `INSERT ... ON DUPLICATE KEY UPDATE` | **有主键/唯一键**的表 | 是 |
| 纯追加 | `INSERT` | 原始日志，且每次都是全新批次 | **否** |

### 4.3 为什么本项目当前选"全量覆盖"

关键判断：**能不能追加，取决于源数据的性质，而不是引擎有没有这个参数。**

- `dim_user_profile` 的来源 `user_face.csv` 是一份**全量快照**（每个用户一行）。对快照而言"新内容"这个概念不存在，正确动作就是覆盖。
- `ods_user_behavior` 的来源是行为日志，**天然是增量**。但本项目没有 `load_date` / `batch_id` 这类批次字段 → **无法区分"新数据"和"上次已导过的数据"** → 只能全量重建。

### 4.4 一个概念纠正

"能加入新内容的才叫可复用"——更准确的说法是：让脚本可复用的性质是**幂等**（跑 1 次和跑 10 次结果一样），而不是 append。
反例就是上表第三行：**纯追加恰恰是最不可复用的**，因为它跑第二遍就毁数据。
全量覆盖之所以可复用，正因为它是幂等的。

> 增量装载（UPSERT）的完整方案见第十一节"未来改进"。

## 十一、未来改进：UPSERT 增量装载（本次不做）

### 11.1 为什么值得单独做

你提出的"必须能加在表的结尾"在工程上对应的是 **UPSERT**，它同时满足你的诉求和幂等要求：

| 情形 | 行为 |
|---|---|
| 新用户 | 插入（真的"加在表的结尾"）|
| 已有用户 | `UPDATE face = 新值`（顺带把脏值刷成干净的）|
| 重复运行 | 结果一致，不报错、不翻倍 |

### 11.2 实现方式与代价

```sql
INSERT INTO dim_user_profile (user_id, face) VALUES (%s, %s)
ON DUPLICATE KEY UPDATE face = VALUES(face);
```

**代价**：pandas 的 `to_sql` **不支持** `ON DUPLICATE KEY UPDATE`，需要自己拼 SQL 用 `executemany` 执行，`load_small_table` 大约要重写 15 行。

### 11.3 为什么本次不做

本次的目标是"清空格 + 验证可复现"。如果顺手把装载模式也换掉，验证对象就从**一个变量**变成了**两个变量**——一旦基准数字不对，无法判断是清洗的问题还是装载模式的问题。**变量要一次只动一个。**

### 11.4 何时做

- 需要接增量批次（比如"每天新增一批评论/行为"）时
- 或者 ODS 表要支持"只追加新批次"时（那还需要先加 `load_date` / `batch_id` 字段）

届时建议单独出一份方案文档，并把三种加载模式用 `DATA_SOURCES` 里的 `load_mode` 字段显式声明出来。
